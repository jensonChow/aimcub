# Desktop Memory

## Product Surface

Desktop is the primary product surface for the local Aim OS agent harness. CLI remains important for setup, scripting, debugging, and automation, but new orchestration UX should land in Desktop first.

Desktop must be product-first, not debug-first. Model calls, tool traces, prompt previews, runtime internals, and planning debug should be opt-in developer surfaces, not default layout columns.

The user rejected the prior over-stacked desktop direction. Do not add more default rails, debug cards, runtime strips, or status boxes to the main view.

Planning, draft, refine, and save failures must show concise product language and a recovery action by default. Raw schema paths, Zod messages, validator dumps, and provider internals belong only behind an explicit Developer details disclosure or debug surface.

Unfinished New Aim work is product data, not a temporary form. Desktop must persist recoverable Aim drafts under the selected local Aimcub data directory before navigation can hide user-entered title, context, answers, generated plan, or save-blocked state. Draft recovery rows in the sidebar and Home panel use one content-entry surface: the row body resumes work, trailing More Actions exposes Resume and Discard, and discard stays menu-gated with inline confirmation instead of visible row text or native dialogs. Drafts must not appear as saved aims until `saveGoal` succeeds.

Desktop navigation is target-first and mutually exclusive: Home, transient New Aim, one persisted draft, or one saved aim owns the current state. A persisted draft replaces New Aim as the selected sidebar item and keeps Aim, Context, and Contracts navigation visible even on its Aim surface; Work and Review exist only for saved aims. Settings must return to the originating target and surface. Startup keeps Home visible when recoverable drafts exist instead of opening an arbitrary saved aim, and every persisted draft must remain reachable.

Draft checkpoints use one stable draft ID and serialized writes per active draft session. Home, New Aim, saved-aim open, and draft-to-draft navigation wait for the latest checkpoint before changing targets; a failed checkpoint keeps the current draft open with a product-facing recovery message. While a target checkpoint or read is pending, the visible old surface cannot start workflow mutations, but a newer target navigation may supersede the pending request. Late draft, planning, or goal responses from an older target transition must not replace the newer target; a response may refresh data for the same Aim after surface navigation, but it must not reroute the user away from the newer surface.

Side-effecting agent runs, proof submissions, and context reviews keep one in-flight lock while the user browses other surfaces so the same action cannot be launched twice. Draft discard locks normal navigation; when the discarded draft is active, it serializes pending writes, blocks further autosave, invalidates any pending activation for that draft, and restores the existing draft session if deletion fails. Discarding an inactive draft must not suppress autosave for the draft the user is still editing.

User-entered or expensive generated work must not be silently destroyed by normal Desktop navigation. Context source selections, manual proof drafts, Settings setup drafts, and any future volatile work surface need either a recoverable local draft checkpoint or an explicit product-facing discard choice before Settings/reload boundaries, Cmd/Ctrl shortcuts, component unmount paths, or other normal navigation can clear them.

## Current Shell

The default desktop shell is a simplified two-column product layout:

- Left sidebar: a floating Glass island (2026-07-13 re-sync) — brand row (accent "A" mark + "Aimcub" → Home, compact "+" → New Aim), a plain aim list, and the footer account trigger. There are no action rows, search field, filters, section labels, or hover keyboard hints; Cmd+K owns navigation shortcuts. Full visual spec (geometry, row metrics, states) lives in `docs/memory/design-system.md`.
- Sidebar Aim and draft entries are compact one-line navigation rows. Their display label prefers a concise generated `goal_summary` and uses conservative intent cleanup plus a grapheme-safe display bound as the pre-plan fallback; the original canonical title remains unchanged for editing, planning, search, CLI, and agents. CSS owns narrower responsive ellipsis, while the focusable row exposes the full cleaned summary. Do not render Context needed, Plan ready, Save blocked, active, paused, or other status subtitles beneath these titles. Keep draft More Actions and selected/current semantics intact.
- Pinned left sidebars expose a transparent resize hot zone with the native resize cursor, not a visible divider, and stable width bounds. The normal Aim sidebar may auto-collapse before medium-width windows squeeze the main workspace, but a user-pinned sidebar must reserve layout space and never cover the workspace; Settings keeps its always-visible category sidebar.
- Footer user menu: the lower-left account trigger owns global controls such as Settings and Language through an account-style popover/menu rather than separate header/footer controls. Keep the popover interior compact and aligned with small labels, tight rows, stable icon/text/action columns, and pointer-open behavior that does not automatically show a first-item focus ring. Language opens as a Claude-like side submenu on hover or keyboard focus, not as an inline click-expanded section.
- Sidebar toggle: outside Settings, a top-left titlebar-cluster icon button controls pinned/collapsed sidebar state. When collapsed, hovering or focusing the button, or hovering the 32 px left-edge reveal rail, reveals a temporary overlay peek sidebar without changing the main workspace width. Clicking to expand creates a pinned sidebar that pushes the workspace instead of covering it.
- Window chrome: normal macOS window mode uses native Electron/macOS traffic lights only, with a Claude/Codex-like main-process shell that positions the native controls. Desktop currently uses Electron 43.0.0; after Electron changes, visually verify that native traffic lights still match the 14 pt Claude/Finder sizing on this machine. Electron 33 rendered them at 12 pt. Renderer code must not draw red/yellow/green or inactive substitute dots. Keep the sidebar toggle after the native traffic-light safe area in normal mode; fullscreen product content moves it left into traffic-light-safe space, but Aimcub must not hide native traffic lights from the macOS fullscreen titlebar when that titlebar is revealed. Desktop follows macOS system light/dark appearance through Electron `nativeTheme`, matching BrowserWindow background colors, and renderer appearance tokens. The Glass sidebar footer adds an explicit light/dark theme toggle: a renderer-owned `localStorage` preference drives the content tokens off `data-system-appearance`, and it is synced to the native window chrome through a `setThemeSource` IPC → `nativeTheme.themeSource` handler (whose `"updated"` listener repaints the window background and re-emits chrome state), so an in-app override does not desync the native titlebar/traffic-light context; "system" hands appearance back to the OS. Detailed visual requirements live in `docs/memory/design-system.md`.
- Center workspace: the initial empty Aim stage is a quiet placeholder with no chat, textarea, continue control, or workflow navigation. The command-composer appears only after the user explicitly starts a New Aim. Saved aim overview and later stage surfaces use compact non-linear workbench navigation above the active task surface: a current-surface label plus a quiet segmented switcher for Aim, Context, Contracts, Work, and Review. Do not render numbered step pills or imply that the surfaces must be completed in order.
- Home with recoverable drafts does not also show the empty Workspace ready placeholder. Its draft recovery surface is vertically centered in the available workspace on the compact compose rail. Recovered Aim summaries are also vertically centered below the workbench navigation, while overflowing content falls back safely to the scrollable start edge. Shared Desktop rails are 560 px for compose/draft lists, 760 px for reading/focused questions, 940 px for operational stages, and 1080 px for Settings; related controls stay start-aligned within their rail instead of drifting to opposite sides of a wide window.
- Aim draft presentation follows a compose-summary-edit state model. New Aim and unsent child breakdown work use the composer; after the first submit and on normal draft recovery, Aim shows a static outcome summary with Edit plus the relevant helper setup, Context, or Contracts action. Draft persistence records compose versus summary explicitly, and legacy recovery fails safe to summary. A missing planning runtime, autosave, navigation, or restart must not return a captured Aim to the composer. Edit is explicit and buffered; the committed Aim and plan stay intact until Update, which restarts planning when required. Normal navigation remains blocked until Update or Cancel. Context never re-embeds the Aim composer, including for child aims, and child Context retains the same Continue/retry planning path as top-level drafts.
- No visible full-width titlebar above the workbench. Keep macOS window controls in sidebar-safe space and keep command palette access keyboard-first.
- Titlebar safety is driven by shell geometry rather than active-stage names or stage-nav presence. With the normal sidebar collapsed or peeking, every non-Settings main workspace clears the native traffic lights plus sidebar toggle, including transient pre-autosave Context/Contracts content; pinned-sidebar pages keep one consistent top baseline because the sidebar already owns that chrome space.
- The app should launch in a compact desktop footprint, currently around 960 by 680 px, and allow resizing down to roughly 640 by 520 px.
- No right inspector/debug rail in the default product shell.

The first-run Aim stage must stay calmer than an intake surface: no idle titlebar status text, no duplicate "New Aim" eyebrow in the main surface, no automatic heavy focus ring, and no large form-like blank textarea before the user starts a New Aim. Once the composer is explicitly opened, the primary action is naming the outcome; context is secondary until the next stage.

Selecting an existing aim should open Aim overview first instead of jumping directly into Run details. Existing aims should not show an empty composer on the Context stage.

Completed aims are the exception to the overview default: if `AimProgressReadModel.completion_recap.complete` is true, Desktop should open the Eval stage and show the completion recap.

The renderer was reset from the old debug-heavy cockpit into a compact Aim OS cockpit MVP. It should keep one primary task per screen and avoid stacking unrelated status/debug/runtime panels.

## Aimcub Glass Shell (active direction)

The desktop is the **Aimcub Glass** visual system + a "Journey" information architecture (a glassmorphism gradient desktop behind translucent blurred islands). Product behavior below is unchanged; Glass restyles the surfaces and reworks the work view. Specifics live in `docs/memory/design-system.md`.

- Work surface: a saved aim opens to the **Journey** view (`renderer/stages/journey/JourneyView.tsx`), which replaces the old `AimOverviewPanel`. It renders from pure, unit-tested helpers under `renderer/workflow/journey/` off the existing `AimProgressReadModel` (+ the run-event journal and the aim's memories): a 6-station strip (Aim · Research · Context · Plan · Run · Eval), one "Your move" card (or an "Ambient" card), a "Turns" roster, and a "Journal" receipt timeline. Clicking a station opens a read-only sheet held in local component state — it never touches the workspace/surface navigation epochs and clears on any real navigation; its footer CTA routes into the interactive stage via `openCockpitStage`. The heavy interactive stage panels (Context/Plan/Execute/Eval) are unchanged and still reached through `openCockpitStage`, so the draft/navigation/proof/side-effect invariants need no plumbing changes.
- Memory is a top-level page (`renderer/stages/memory/MemoryView.tsx`) over a `listMemories` IPC: active memories grouped by category with provenance and a Forget action (reusing `archiveContextMemory`), plus an honest empty state. It is a non-workbench overlay stage driven by `stageOverride`, mirroring Settings. A sidebar Memory nav row + a `~/.aimcub · local` footer + the theme toggle sit below the recent-aims list.
- List surfaces show a per-aim rollup as a small status **dot** marker (never a subtitle): sidebar aim rows carry the dot; Home cards add a 6px progress bar + `{done}/{total}`. These read from a cheap batch `listAimProgressSummaries` IPC (one store pass) rather than N `getAimProgress` calls. The run-lifecycle Journal reads from a separate `getAimJournal` IPC over persisted run events, kept off the hot `getAimProgress`.

## Renderer Structure

`apps/desktop/src/renderer/App.tsx` should stay orchestration-focused: state, IPC calls, stage routing, and handoffs between stage surfaces. Stage-owned view structure lives under `apps/desktop/src/renderer/stages/<stage>/`, currently `context`, `plan`, `eval`, and `execute`. Do not reintroduce large inline Context, Plan/Contracts, Eval, or Execute component bodies into `App.tsx`.

Pure renderer workflow transforms shared by App orchestration live under `apps/desktop/src/renderer/workflow/`. Keep these helpers side-effect-free and directly unit-tested; leave IPC calls and visible state transitions in `App.tsx` unless a behavior-specific test covers the abstraction.

Shared renderer primitives live under `apps/desktop/src/renderer/ui/`. Reuse or extend those primitives for low-risk workbench/helper surfaces before adding new one-off control styling, while keeping the protected shell/sidebar/window-chrome framework unchanged.

## Stage Polish Defaults

The Desktop stage loop stays product-first without expanding scope. Context should omit empty review surfaces in the default ready flow and show a single Continue to Plan action only when no intake question or refinement panel is active. When collection is active without a user question, show activity and sufficiency derived from existing renderer signals: planning live events, planning context/tool traces, intake, review buckets, answers, notes, and source status. Blocking Context intake becomes a focused question surface rather than sharing the screen with that overview.

Plan/Contracts should keep contract review primary with a compact contract selector and one selected summary-first contract: title, selected route, validation state when present, definition of done, required evidence, and routing rationale stay visible by default, while description/body, why, full eval signal, detailed routing controls, and structure edits stay behind secondary disclosures. Never stack every editable contract detail on the page. Mark contracts with routing or rule errors in the selector, keep repair controls enabled, and block structure edits while an invalid rule draft could be discarded. Reset selector, disclosure, and rule-draft state after a successful target change so one draft cannot contaminate another. Omit an empty Context bundle review above Contracts; keep a non-empty review in a default-closed counted disclosure so Save and the current contract remain primary. Raw `acceptance_rule` JSON belongs only under Developer details. Draft/refine/save planning failures should use product-facing language and recovery routes; raw validation/provider details belong behind Developer details. Validation failures must disable Save until the plan is executable, but must not disable the contract-edit controls needed for repair.

Execute should prioritize selected sub-aim, selected owner/local agent, run state, evidence state, and next human/eval action; runtime metadata stays secondary, and raw `agent.raw` or `agent.message.delta` events stay out of default activity. Eval should lead with trust overview metrics and summary-first milestone cards, with evidence rows and evaluator details behind secondary disclosures while Context Inbox remains part of the Eval flow only when pending candidates exist.

The Execute stage durable default is a selected-work pattern: a bounded, independently scrolling sub-aim selector, one selected execution detail surface, and one state-dependent primary action placed before runtime and activity details. Run agent is primary only for agent-routed incomplete work, Submit proof is primary only for human-routed incomplete work, Review in Eval is primary for completed or low-trust work, and blocked work must show the blocker plus next recovery action. Break Down and alternate run/proof actions stay visually secondary. Runtime and activity stay in a default-closed disclosure. An open proof form replaces the normal action group, disables sub-aim switching, and blocks normal target or workbench navigation until submit or cancel; a failed confirmation preserves the form and values. Once confirmation succeeds, close the submitted draft even if the follow-up progress refresh fails, then report the refresh error separately so retry cannot append duplicate evidence. Focus moves into the form on open and returns to its trigger on cancel. Detailed evidence/evaluator reasoning belongs in Eval, and the local CLI runtime behavior should not change for this polish layer.

## Context Collection

Desktop context collection is a first-class setup layer. `context-sources.json` records linked local folders, explicit local files, online connector references, web/deep-research preference, dedicated context session toggle, and choice-question toggle.

Planning consumes context before decomposition through `context.linked_sources`, `local.read`, optional `web.search`/`web.fetch`, `context.distill`, and structured user questions. Web research is planned as bounded lanes for aim facts, authoritative requirements, alternatives/market evidence, risks/tradeoffs, and user/audience evidence when relevant. The resulting brief preserves source URLs and reports coverage, authority, freshness, conflicts, uncertainty, and sufficiency instead of treating any search result list as automatically complete. Connector references are locations or access gaps until a runtime can actually read them.

The default Context stage workbench is sparse and stepwise: show one blocking intake question at a time, then aim-local file/folder attachment, then planning/review state only after tool context or review items exist, and a single Continue to Plan action when no question or refinement panel is active. Do not put provider setup, web capability, online connector setup, permission setup, or planning gate tables in the default workbench. Omit empty context-review buckets so skipped/unread context, permission/setup gaps, and decomposition risks appear only when they exist.

An active blocking question or optional draft refinement is a focused task surface, not another band in the Context overview. Hide the Aim summary and edit action, activity/sufficiency pipeline, source controls, and bundle review until the user leaves that question flow. Keep exactly one question visible, preserve it while multi-select or custom text changes, and advance only from the bottom Next action. Pre-draft intake is adaptive: after each answer, Desktop sends the cumulative questions and answers back through the same intake run, appends one non-duplicate follow-up, and stops when the model reports sufficient context or the bounded turn cap is reached. Pending draft refinement must remain active across repeated Context-tab clicks, stage re-entry, and draft hydration; only successful refinement or explicit accept/skip completes it, while its questions and answers remain available for draft persistence and final save metadata. A question-specific custom response and the general context note must never appear together. If both questionnaire and context-session input are paused, show one Open Settings recovery action instead of an empty or disabled form.

Desktop consumes the shared normalized question mode and owns its hydration semantics. On hydration, legacy questions are re-normalized, duplicate option labels and exact duplicate answer labels are removed, and ambiguous or unknown values that remain in the normalized legacy label set move into visible custom text instead of being dropped.

`ContextSourcesPanel` has two intentional surfaces. The workbench variant is for current-aim local material plus a Settings handoff. The settings variant keeps the full context-source setup summary, compact readiness gates, and one editable control surface for local paths, online references, web/deep-research preference, context session, and choice-question controls.

The Context and Sub-aims stages show a default context bundle review before/inside planning. It classifies used context, skipped/unread context, permission/setup gaps, and unresolved decomposition risks from planning context reports, tool traces, intake questions, review gaps, and plan contract gaps.

User-facing intake questions should come from `generateAimIntakeQuestions` grounded in available context. Do not surface template prompts like "Ask for..." directly to users.

When web research is enabled and relevant, Desktop prefers a configured Brave search key. If no key is configured, an authenticated local Codex or Claude CLI can supply the bounded live-search corpus; missing, unavailable, or unauthenticated runtimes remain explicit planning gaps rather than fabricated research. Page fetching and the shared coverage/sufficiency layer remain provider-independent.

The main Desktop loop reaches Context Inbox from the Eval stage. Pending context candidates render as editable review rows with source, category, confidence, and scope; accept/reject uses the existing context-candidate IPC. Accepting global context makes it active memory for future aim planning, while accepting aim scope keeps it tied to the current aim.

## Embedded Planning Session (Desktop surface)

The aim process is one continuous flow (simplified 2026-07-24, founder-directed): CREATING an aim starts planning immediately — `createAimAndOpenJourney` mints the shell, opens the Journey, and auto-starts the embedded session (or the funnel when no brain is session-ready); there is no separate "Build the plan" click for a fresh aim (the card + explicit start remain for replans and runtime-not-ready). The embedded path never leaves the Journey: the session panel (working state, questions, chat, failure) mounts through JourneyView's `planning.clarifyPanel` slot; when the session lands, the slot empties and the Journey's in-place plan review + save CTA take over (`applySessionLanding` sets mode `reviewing` and does NOT hop to the contracts stage — the funnel keeps its own stage choreography). The Context stage still shows the session when visited manually. Beside the planning card there is only a quiet "Brain · model" status chip opening Settings → Brain.

The session-ready brain is chosen by `resolvePlanningBrain` (explicit `planningBrain` pref when session-ready, else first capable in registry order); the funnel remains the automatic fallback (no brain, spawn failure, or session failure → `startDraft` on the same shell). Main owns the session in `apps/desktop/src/main/planning-session.ts`: one session per goalId, broadcast state pushes over `planningSessionEvent` (same pattern as `runLiveEvent`, because sessions outlive navigation), a compact activity ring buffer, and the landing bundle (plan + quality + `reviewPlan` + session Q&A mapped to the funnel's question/answer shapes + disclosed assumptions) computed at `draft_ready`. `updateGoalPlan` in planning-run mode attaches the serialized session (`metadata.planning_session`), records the brain's proposed facts as PENDING memory candidates (`agent_inferred`; category kept only when it parses as a `ContextCategory`), and releases the session. Brains are child processes: `before-quit` cancels all sessions.

Renderer invariants: the session surface mounts through the Context stage's existing focused-panel slot (`clarifyPanel` + a forced `"intake"` phase), so the focused-question rules hold unchanged; a blocking question renders through `ContextClarifyPanel` itself (session question payloads are ClarifyQuestion-compatible) with the general context note disabled — a question-specific answer and the note never appear together. The live (no-question) view shows compact activity, the temporary-chat composer, Draft-now, and Stop. Chat and one-question answer state live in App state so navigation does not destroy them; the renderer re-attaches to a running session on goal selection via `getPlanningSessionState`. Session landing mirrors `refinePlan`'s terminal state (mode `reviewing`, stage `contracts`) and commits through the same `commitShellPlan`. Session activity/busy must NOT set the global busy lock — the chat composer stays interactive while the brain works.

## Local Agents

The shared local CLI adapter lives in `packages/local-agent`; Desktop keeps compatibility re-exports at its former main-process paths. The adapter detects Codex and Claude CLIs through explicit env overrides, PATH, common install paths, version/auth/model probes, command construction, stdin prompt delivery, and JSONL/stream-json event normalization. Desktop and CLI use the same runtime for planning fallback and selected sub-aim execution.

This harness is an Aimcub runtime layer, not MCP. Aimcub owns aim decomposition, context, permissions, evidence, and eval; local CLIs are execution runtimes when no API provider is configured or when the user chooses local execution.

Network access stays purpose-bound. Desktop may enable live search for relevant web research; the general `aimcub run` execution path enables network only with `--network`. A CLI run handles one dependency-ready agent-owned sub-aim, persists normalized run events and low-trust evidence, and returns control to Aimcub eval. It is not a daemon or an until-blocked orchestration loop, and agent output does not directly mark work complete.

Desktop settings use the app's primary left sidebar as category navigation and the center workspace as the selected detail pane. Settings mode locks that sidebar open and does not show the normal Aim workspace sidebar toggle, peek rail, or `Aimcub / Workbench` brand header. Settings sidebar controls, including Back, search, section labels, nav rows, and the footer trigger, must share the main sidebar's content width, row inset, icon column, and text baseline. The Settings search field uses a Codex-like inline magnifying-glass icon in that shared icon column. Selected Settings nav rows use a quiet Codex-like gray fill without a blue active rail; status dots may remain as readiness signals. Settings detail rows use Codex-like thin bordered rounded control groups with internal dividers, without turning helper setup into decorative cards. Detail row status reads as muted text plus a tiny readiness dot, and row actions use quiet gray control surfaces so the settings pane does not read like a colored status report. The Settings workspace may use a wider Codex-like control panel width around 1080 px while keeping header copy narrower. Provider setup, local CLI agent detection, web research, and context sources stay separated by category instead of stacked into one long page or nested behind a second workspace sidebar. The "Local CLI agents" detail pane includes detection and explicit read-only smoke tests; keep it thin until milestone execution and evidence capture are deeper.
