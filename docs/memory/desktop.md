# Desktop Memory

## Product Surface

Desktop is the primary product surface for the local Aim OS agent harness. CLI remains important for setup, scripting, debugging, and automation, but new orchestration UX should land in Desktop first.

Desktop must be product-first, not debug-first. Model calls, tool traces, prompt previews, runtime internals, and planning debug should be opt-in developer surfaces, not default layout columns.

The user rejected the prior over-stacked desktop direction. Do not add more default rails, debug cards, runtime strips, or status boxes to the main view.

Planning, draft, refine, and save failures must show concise product language and a recovery action by default. Raw schema paths, Zod messages, validator dumps, and provider internals belong only behind an explicit Developer details disclosure or debug surface.

Unfinished New Aim work is product data, not a temporary form. Desktop must persist recoverable Aim drafts under the selected local Aimcub data directory before navigation can hide user-entered title, context, answers, generated plan, or save-blocked state. Draft recovery rows in the sidebar and Home panel use one content-entry surface: the row body resumes work, trailing More Actions exposes Resume and Discard, and discard stays menu-gated with inline confirmation instead of visible row text or native dialogs. Drafts must not appear as saved aims until `saveGoal` succeeds.

Desktop navigation is target-first and mutually exclusive: Home, transient New Aim, one persisted draft, or one saved aim owns the current state. The stage model is collapsed to `aim | settings | memory`: a draft is composer-only, and a saved aim's whole loop lives on the Journey. Settings returns to the Journey (or Home) it came from. Startup keeps Home visible when recoverable drafts exist instead of opening an arbitrary saved aim, and every persisted draft must remain reachable.

Draft checkpoints use one stable draft ID and serialized writes per active draft session. Home, New Aim, saved-aim open, and draft-to-draft navigation wait for the latest checkpoint before changing targets; a failed checkpoint keeps the current draft open with a product-facing recovery message. While a target checkpoint or read is pending, the visible old surface cannot start workflow mutations, but a newer target navigation may supersede the pending request. Late draft, planning, or goal responses from an older target transition must not replace the newer target; a response may refresh data for the same Aim after surface navigation, but it must not reroute the user away from the newer surface.

Side-effecting agent runs, proof submissions, and context reviews keep one in-flight lock while the user browses other surfaces so the same action cannot be launched twice. Draft discard locks normal navigation; when the discarded draft is active, it serializes pending writes, blocks further autosave, invalidates any pending activation for that draft, and restores the existing draft session if deletion fails. Discarding an inactive draft must not suppress autosave for the draft the user is still editing.

User-entered or expensive generated work must not be silently destroyed by normal Desktop navigation. Context source selections, manual proof drafts, Settings setup drafts, and any future volatile work surface need either a recoverable local draft checkpoint or an explicit product-facing discard choice before Settings/reload boundaries, Cmd/Ctrl shortcuts, component unmount paths, or other normal navigation can clear them.

## Current Shell

The default desktop shell is a simplified two-column product layout:

- Left sidebar: a floating Glass island (2026-07-13 re-sync) — brand row (accent "A" mark + "Aimcub" → Home, compact "+" → New Aim), a plain aim list, and the footer account trigger. There are no action rows, search field, filters, section labels, or hover keyboard hints; Cmd+K owns navigation shortcuts. Full visual spec (geometry, row metrics, states) lives in `docs/memory/design-system.md`.
- Sidebar Aim and draft entries are compact one-line navigation rows. Aim rows carry a hover/focus-revealed More Actions menu whose one destructive item, Delete aim, sits behind an inline confirmation; main cancels any planning session for the aim before the store's `deleteGoal` cascade, the renderer stops a live run it can see, and deleting the open aim lands on Home. Archive-with-restore is the designed follow-up if shelving real aims becomes the need. Their display label prefers a concise generated `goal_summary` and uses conservative intent cleanup plus a grapheme-safe display bound as the pre-plan fallback; the original canonical title remains unchanged for editing, planning, search, CLI, and agents. CSS owns narrower responsive ellipsis, while the focusable row exposes the full cleaned summary. Do not render Context needed, Plan ready, Save blocked, active, paused, or other status subtitles beneath these titles. Keep draft More Actions and selected/current semantics intact.
- Pinned left sidebars expose a transparent resize hot zone with the native resize cursor, not a visible divider, and stable width bounds. The normal Aim sidebar may auto-collapse before medium-width windows squeeze the main workspace, but a user-pinned sidebar must reserve layout space and never cover the workspace; Settings keeps its always-visible category sidebar.
- Footer user menu: the lower-left account trigger owns global controls such as Settings and Language through an account-style popover/menu rather than separate header/footer controls. Keep the popover interior compact and aligned with small labels, tight rows, stable icon/text/action columns, and pointer-open behavior that does not automatically show a first-item focus ring. Language opens as a Claude-like side submenu on hover or keyboard focus, not as an inline click-expanded section.
- Sidebar toggle: outside Settings, a top-left titlebar-cluster icon button controls pinned/collapsed sidebar state. When collapsed, hovering or focusing the button, or hovering the 32 px left-edge reveal rail, reveals a temporary overlay peek sidebar without changing the main workspace width. Clicking to expand creates a pinned sidebar that pushes the workspace instead of covering it.
- Window chrome: normal macOS window mode uses native Electron/macOS traffic lights only, with a Claude/Codex-like main-process shell that positions the native controls. Desktop currently uses Electron 43.0.0; after Electron changes, visually verify that native traffic lights still match the 14 pt Claude/Finder sizing on this machine. Electron 33 rendered them at 12 pt. Renderer code must not draw red/yellow/green or inactive substitute dots. Keep the sidebar toggle after the native traffic-light safe area in normal mode; fullscreen product content moves it left into traffic-light-safe space, but Aimcub must not hide native traffic lights from the macOS fullscreen titlebar when that titlebar is revealed. Desktop follows macOS system light/dark appearance through Electron `nativeTheme`, matching BrowserWindow background colors, and renderer appearance tokens. The Glass sidebar footer adds an explicit light/dark theme toggle: a renderer-owned `localStorage` preference drives the content tokens off `data-system-appearance`, and it is synced to the native window chrome through a `setThemeSource` IPC → `nativeTheme.themeSource` handler (whose `"updated"` listener repaints the window background and re-emits chrome state), so an in-app override does not desync the native titlebar/traffic-light context; "system" hands appearance back to the OS. Detailed visual requirements live in `docs/memory/design-system.md`.
- Center workspace: the initial empty Aim stage is a quiet placeholder with no chat, textarea, continue control, or workflow navigation. The command-composer appears only after the user explicitly starts a New Aim. A saved aim renders the Journey as its ONLY surface — there is no workbench stage navigation of any kind (Collapse, 2026-07-25).
- Home with recoverable drafts does not also show the empty Workspace ready placeholder. Its draft recovery surface is vertically centered in the available workspace on the compact compose rail. Recovered Aim summaries are also vertically centered below the workbench navigation, while overflowing content falls back safely to the scrollable start edge. Shared Desktop rails are 560 px for compose/draft lists, 760 px for reading/focused questions, 940 px for operational stages, and 1080 px for Settings; related controls stay start-aligned within their rail instead of drifting to opposite sides of a wide window.
- Aim draft presentation follows a compose-summary-edit state model. New Aim and unsent child breakdown work use the composer; after the first submit and on normal draft recovery, Aim shows a static outcome summary with Edit plus the relevant helper setup, Context, or Contracts action. Draft persistence records compose versus summary explicitly, and legacy recovery fails safe to summary. A missing planning runtime, autosave, navigation, or restart must not return a captured Aim to the composer. Edit is explicit and buffered; the committed Aim and plan stay intact until Update, which restarts planning when required. Normal navigation remains blocked until Update or Cancel. Context never re-embeds the Aim composer, including for child aims, and child Context retains the same Continue/retry planning path as top-level drafts.
- No visible full-width titlebar above the workbench. Keep macOS window controls in sidebar-safe space and keep command palette access keyboard-first.
- Titlebar safety is driven by shell geometry rather than active-stage names or stage-nav presence. With the normal sidebar collapsed or peeking, every non-Settings main workspace clears the native traffic lights plus sidebar toggle, including transient pre-autosave Context/Contracts content; pinned-sidebar pages keep one consistent top baseline because the sidebar already owns that chrome space.
- The app should launch in a compact desktop footprint, currently around 960 by 680 px, and allow resizing down to roughly 640 by 520 px.
- No right inspector/debug rail in the default product shell.

The first-run Aim stage must stay calmer than an intake surface: no idle titlebar status text, no duplicate "New Aim" eyebrow in the main surface, no automatic heavy focus ring, and no large form-like blank textarea before the user starts a New Aim. Once the composer is explicitly opened, the primary action is naming the outcome; context is secondary until the next stage.

Selecting an existing aim opens its Journey. If `AimProgressReadModel.completion_recap.complete` is true, the Journey leads with the completion recap in place of the live lane and plan rows.

The renderer was reset from the old debug-heavy cockpit into a compact Aim OS cockpit MVP. It should keep one primary task per screen and avoid stacking unrelated status/debug/runtime panels.

Shared renderer primitives live under `apps/desktop/src/renderer/ui/`. Reuse or extend those primitives for low-risk workbench/helper surfaces before adding new one-off control styling, while keeping the protected shell/sidebar/window-chrome framework unchanged.

## Work-Detail Defaults (plan rows)

The Journey's plan band keeps the old Execute-stage invariants: one expanded row at a time; a state-dependent primary action placed before runtime and activity details (Run agent only for agent-routed incomplete work with a complete permission grant; Submit proof only for human-routed incomplete work; completed/low-trust rows show receipts inline with NO primary button); Break down and alternate run/proof actions stay secondary; runtime metadata and activity stay in default-closed disclosures; raw `agent.raw`/`agent.message.delta` events stay out of default activity. An open proof form replaces the row's normal detail, disables switching rows, and blocks normal navigation until submit or cancel; a failed confirmation preserves the form and values; a successful confirmation closes the draft even if the follow-up refresh fails, and the refresh error reports separately so retry cannot append duplicate evidence. Run consent is per sub-aim and per session, never persisted; a workspace-write grant is incomplete until its folder is picked; the cockpit never offers `danger-full-access`. Eval receipts (evidence review + evaluator matches) live behind closed disclosures on the row, auto-open when review is the row's next action.

## Context Collection

Desktop context collection is a first-class setup layer. `context-sources.json` records linked local folders, explicit local files, online connector references, web/deep-research preference, dedicated context session toggle, and choice-question toggle.

Planning consumes context before decomposition through `context.linked_sources`, `local.read`, optional `web.search`/`web.fetch`, `context.distill`, and structured user questions. Web research is planned as bounded lanes for aim facts, authoritative requirements, alternatives/market evidence, risks/tradeoffs, and user/audience evidence when relevant. The resulting brief preserves source URLs and reports coverage, authority, freshness, conflicts, uncertainty, and sufficiency instead of treating any search result list as automatically complete. Connector references are locations or access gaps until a runtime can actually read them.

Context collection surfaces through the Journey's live lane (the planning session or funnel asks one question at a time); there is no Context stage page. Provider setup, web capability, online connector setup, and permission setup live in Settings.

An active blocking question or optional draft refinement is a focused task surface: it owns the live lane, keeps exactly one question visible, preserves selections while multi-select or custom text changes, and advances only from the bottom Next action. Pre-draft intake stays adaptive and bounded. A question-specific custom response and the general context note must never appear together. If both questionnaire and context-session input are paused, show one Open Settings recovery action instead of an empty or disabled form.

Desktop consumes the shared normalized question mode and owns its hydration semantics. On hydration, legacy questions are re-normalized, duplicate option labels and exact duplicate answer labels are removed, and ambiguous or unknown values that remain in the normalized legacy label set move into visible custom text instead of being dropped.

`ContextSourcesPanel` has one surface: the Settings → Research pane's full context-source setup summary, compact readiness gates, and one editable control surface for local paths, online references, web/deep-research preference, context session, and choice-question controls. The old workbench variant was deleted with the Context stage.

User-facing intake questions should come from `generateAimIntakeQuestions` grounded in available context. Do not surface template prompts like "Ask for..." directly to users.

When web research is enabled and relevant, Desktop prefers a configured Brave search key. If no key is configured, an authenticated local Codex or Claude CLI can supply the bounded live-search corpus; missing, unavailable, or unauthenticated runtimes remain explicit planning gaps rather than fabricated research. Page fetching and the shared coverage/sufficiency layer remain provider-independent.

Pending context candidates render as an inline review band on the Journey (only when candidates exist), with editable rows carrying source, category, confidence, and scope; accept/reject uses the existing context-candidate IPC. Accepting global context makes it active memory for future aim planning, while accepting aim scope keeps it tied to the current aim.

## Embedded Planning Session (Desktop surface)

The aim process is one continuous flow (simplified 2026-07-24, founder-directed): CREATING an aim starts planning immediately — `createAimAndOpenJourney` mints the shell, opens the Journey, and auto-starts the embedded session (or the funnel when no brain is session-ready); there is no separate "Build the plan" click for a fresh aim (the card + explicit start remain for replans and runtime-not-ready). Planning never leaves the Journey — for the session AND the funnel: the session panel (working state, questions, chat, failure) and the funnel's clarify panel both mount through JourneyView's `planning.clarifyPanel` slot; when planning lands, the slot empties and the Journey's in-place plan review + adopt CTA take over. Every planning failure routes back to the Journey (`routeAfterPlanningFailure` → stage "aim"). Beside the planning card there is only a quiet "Brain · model" status chip opening Settings → Brain.

The session-ready brain is chosen by `resolvePlanningBrain` (explicit `planningBrain` pref when session-ready, else first capable in registry order); the funnel remains the automatic fallback (no brain, spawn failure, or session failure → `startDraft` on the same shell). Main owns the session in `apps/desktop/src/main/planning-session.ts`: one session per goalId, broadcast state pushes over `planningSessionEvent` (same pattern as `runLiveEvent`, because sessions outlive navigation), a compact activity ring buffer, and the landing bundle (plan + quality + `reviewPlan` + session Q&A mapped to the funnel's question/answer shapes + disclosed assumptions) computed at `draft_ready`. `updateGoalPlan` in planning-run mode attaches the serialized session (`metadata.planning_session`), records the brain's proposed facts as PENDING memory candidates (`agent_inferred`; category kept only when it parses as a `ContextCategory`), and releases the session. Brains are child processes, so `before-quit` must kill them — but it CHECKPOINTS every live pass first (2026-07-26; cancelling without saving is what erased a whole planning pass on quit). Same slot, `metadata.planning_session`: the landing write and the in-flight checkpoints agree by construction. Contract in `architecture.md`.

Renderer invariants: the session surface mounts through the Journey's planning slot; a blocking question renders through `ContextClarifyPanel` itself (session question payloads are ClarifyQuestion-compatible) with the general context note disabled — a question-specific answer and the note never appear together. The live (no-question) view is one pulsing title + the THOUGHT TRACE + the session receipt + an on-demand note lane + quiet Draft-now/Stop (visual contract in design-system.md). Activity voice is renderer-owned: main's `PlanningSessionActivityItem` carries structure only (kind/code/tool/count) and `planningActivityLine`/`planningActivityTrace` (workflow/planningSession.ts) map it to localized lines, dropping anything unsayable — raw event types and tool ids never render.

**A returning aim shows its paused pass, never a blank start card (2026-07-26).** When no session is live, the Journey reads the aim's last checkpointed pass and mounts `PlanningPassPanel` in place of the build-plan card. Lane precedence, all tested: a LIVE session outranks a checkpoint, a checkpoint outranks the start card, and an aim with a plan ignores both. The start card survives only for an aim that genuinely was never planned — it was never the wrong card, only the wrong card THERE. The panel mirrors the live card (same island, thought trace, receipt footer) with two honest differences: the dot is static (`od-journey-dot-idle`) and the last trace line is NOT marked current, because nothing is happening. Its trace is projected from the persisted transcript onto the live `PlanningSessionActivityItem` structure (`workflow/planningPass.ts`) so the paused surface speaks through the EXISTING voice layer instead of a second dialect; unrecognized entries drop rather than being guessed at. A pass that drafted a plan offers "Review the plan" (adopting it carries the restored Q&A/assumptions into `updateGoalPlan` — a plan adopted after a restart must land like one adopted in the moment), otherwise "Resume planning", with "Plan from scratch" as the quiet escape. An empty pass is not shown at all: it describes no work, so the aim is honestly not planned yet.

**Trace tense is derived from row position, never written into the copy (2026-07-26).** A finished step must read as finished — "Read the aim and your context", not "Reading" under a grey tick (founder). `planningActivityLine` takes a tense; only the last row of a LIVE trace is `now`, everything above it is `done`, and a stopped pass has no current row at all. Two lines carry a completed form (`planningSession.done.started`, `.planRejected`); the rest already record something that happened. A tool line — a working verb with no honest past tense — returns null when asked for a history rendering, so "Searching the web" is structurally unable to sit under a finished tick or to freeze as the last line of a paused pass.

**The user can hand files to a running brain (2026-07-26).** Local files were reachable only through Settings → Research → Manage sources: global, shared by every aim, and never offered where a user would reach for one. The live card's note lane now carries "Attach files" beside "Add a note" — the same act, at the moment you are watching it research and think "it should read this"; the global list stays as a standing default that per-aim attachments add to. Mechanism (`main/planning-attachments.ts`): the brain reads local files with its RUNTIME's own tools, sandboxed by `extraAllowedDirs`, which is baked into the process arguments at spawn — so every session gets an empty staging directory created before spawn and granted through `workspaceRoots`, and attaching COPIES the file in. Naming the user's own path instead would produce a confident-looking read failure. Copies, not symlinks: a runtime that refuses to follow a link out of its sandbox would fail in exactly this case. The brain then hears about them over the ordinary user-message channel, so an attachment lands like a typed note. Per-file failures (a folder, >64 MB, unreadable) are reported on the lane, never dropped — the rest of the selection still goes through. The pass records ORIGINAL paths (`AimDraftPlanningSession.attachments`), because the staging directory dies with its process: a resumed pass re-stages from them and tells the resumed brain the NEW paths, and a source that has since moved says so rather than letting the pass plan against material it no longer has.

**Planning passes leave Journal receipts (2026-07-26).** The Journal read only runs and evidence, so planning left no receipt under a subtitle promising every pass leaves one. `planningPassJournal` derives the pass's MILESTONES — started, each question the user actually answered (attributed to THEM), the research total, plan drafted, how it stopped — merged into `buildJourneyJournal`'s third argument. Not every step: step-by-step belongs to the card's thought trace, and a ledger reprinting tool calls would bury the run receipts. `JourneyJournalEntry.detailVars` carries counts and question text. Receipts are read for PLANNED aims too, but only a plan-less aim requests the landing rebuild (`getPlanningPass({ withLanding })`) — it costs a plan-quality recomputation that is waste where nothing can be adopted.

**Attachment is derived from what is ON SCREEN, never from a renderer-local "I started it" flag** (2026-07-25, founder: "every time I retap into the aim, the whole process will restart"). Main is the authority: sessions outlive navigation and `startPlanningSession` reuses an unsettled session, so the renderer must re-attach rather than re-start. `applySessionView` sets `planningShellId` whenever the view's goal is the selected goal, and a `draft_ready` landing applies on the same condition — so a session that finished off-screen lands when the user returns. `openGoal` clears `planningShellId` only when the target is a DIFFERENT aim (the re-attach effect keys on `selected.id` and will not refire for a re-tap). Gating either the surface or the landing on a start-time flag reintroduces the restart bug. Chat and one-question answer state live in App state so navigation does not destroy them. Session landing sets mode `reviewing` on the Journey and commits through the same `commitShellPlan`. Session activity/busy must NOT set the global busy lock — the note composer stays interactive while the brain works.

## Local Agents

The shared local CLI adapter lives in `packages/local-agent`; Desktop keeps compatibility re-exports at its former main-process paths. The adapter detects Codex and Claude CLIs through explicit env overrides, PATH, common install paths, version/auth/model probes, command construction, stdin prompt delivery, and JSONL/stream-json event normalization. Desktop and CLI use the same runtime for planning fallback and selected sub-aim execution.

This harness is an Aimcub runtime layer, not MCP. Aimcub owns aim decomposition, context, permissions, evidence, and eval; local CLIs are execution runtimes when no API provider is configured or when the user chooses local execution.

Network access stays purpose-bound. Desktop may enable live search for relevant web research; the general `aimcub run` execution path enables network only with `--network`. A CLI run handles one dependency-ready agent-owned sub-aim, persists normalized run events and low-trust evidence, and returns control to Aimcub eval. It is not a daemon or an until-blocked orchestration loop, and agent output does not directly mark work complete.

Desktop settings use the app's primary left sidebar as category navigation and the center workspace as the selected detail pane. Settings mode locks that sidebar open and does not show the normal Aim workspace sidebar toggle, peek rail, or `Aimcub / Workbench` brand header. Settings sidebar controls, including Back, search, section labels, nav rows, and the footer trigger, must share the main sidebar's content width, row inset, icon column, and text baseline. The Settings search field uses a Codex-like inline magnifying-glass icon in that shared icon column. Selected Settings nav rows use a quiet Codex-like gray fill without a blue active rail; status dots may remain as readiness signals. Settings detail rows use Codex-like thin bordered rounded control groups with internal dividers, without turning helper setup into decorative cards. Detail row status reads as muted text plus a tiny readiness dot, and row actions use quiet gray control surfaces so the settings pane does not read like a colored status report. The Settings workspace may use a wider Codex-like control panel width around 1080 px while keeping header copy narrower. Provider setup, local CLI agent detection, web research, and context sources stay separated by category instead of stacked into one long page or nested behind a second workspace sidebar. The "Local CLI agents" detail pane includes detection and explicit read-only smoke tests; keep it thin until milestone execution and evidence capture are deeper.
